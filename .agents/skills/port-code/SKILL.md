# Port code to another language

The old code is the specification. A module is ported when a script says the two implementations
behave the same, not when a reader thinks they do.

## 0. The owner decides it is worth it

Write the reason and a number that will show it worked (latency, memory, cost, one runtime fewer)
in the tracker. Without that, do not start.

## 1. Freeze the outside

What callers see does not change during the port: HTTP shapes, database schema, CLI flags, file
formats, environment variable names. Put the schemas in the contracts folder and, where you can,
generate the types for both languages from that one source.

## 2. Build the oracle before any port

The oracle is a command that runs the **old** implementation on a case and prints the result as
text. Case files hold lines of `input => expected`, generated by the oracle, never typed by hand.

- For a module: the function's inputs and outputs in a plain text or JSON form.
- For a service: recorded requests and responses, with secrets and personal data removed.

The parity test in the new language reads the same files. Protect the oracle, the case files and
the parity test in `.agents/protected-paths`. Write cases for every item under "What differs
between languages" that applies.

## 3. Keep a ledger

Copy `ledger.md`. One row per module: old path, new path, what it depends on, its case file, its
status. Port leaves first, then what depends on them.

## 4. One module per slice

Copy `port-brief.md`. The worker gets the old source, the target file, the case file and the oracle
command, and is told to ask the oracle about cases of its own. Translate behaviour and keep the
structure and names close to the old code: a port that also redesigns cannot be compared. Making it
idiomatic comes after cutover.

## 5. Gate with cases the worker has not seen

`scripts/check.sh` runs the parity tests. Before you accept a slice, generate fresh cases with the
oracle, aimed at the "what differs" list, and run the port on them. This is a script, not a review.

## 6. A difference is a decision

Copy `differences.md`. Every place the new code behaves differently on purpose goes there with the
reason, the date and who agreed. A difference that a parity failure reveals and that is not on the
list is a bug. A bug in the old code is ported as it is, listed, and fixed after cutover in its own
pull request.

## 7. Run both, then cut over

Before the switch, run old and new side by side on real inputs and log every mismatch. Then move
reads, then writes, then retire the old path. Keep the rollback until an agreed number of clean
days has passed.

## 8. Delete the old code

In the same week as cutover. Two live implementations drift. Then refactor the new code to be
idiomatic, with the `adopt-guidelines` skill from step 6.

## What differs between languages

Make cases for each line that applies. Most port bugs are here, not in the logic.

- **Rounding.** JavaScript `Math.round` sends ties towards +∞ (-0.5 → 0). Rust `f64::round` sends
  them away from zero (-0.5 → -1). Python `round` sends them to the even neighbour (0.5 → 0).
- **Number width.** JavaScript has only 64-bit floats: exact to 2^53, no overflow error. Rust
  integers overflow (panic in debug, wrap in release) and Python integers never do.
- **Division and remainder of negatives.** `-7 % 3` is -1 in JavaScript and Rust, 2 in Python.
- **NaN and infinity.** Whether they can occur, how they compare, how they print.
- **Text length and indexing.** UTF-16 units in JavaScript, bytes in Rust, code points in Python.
- **Sorting.** JavaScript's default sort compares as strings. Stability and locale rules differ.
- **Map order.** Insertion order in JavaScript and Python. None in a Rust `HashMap`.
- **Absent values.** `undefined`, `null` and a missing key are three things in JavaScript and one
  `Option` in Rust. Decide what each becomes in JSON.
- **JSON output.** `1` or `1.0`, key order, escaping of non-ASCII.
- **Dates.** What a lenient parser accepted; seconds, milliseconds or nanoseconds; time zones.
- **Regular expressions.** Rust's `regex` has no look-around or back-references.
- **Errors.** Messages or codes that callers match on must stay byte-identical.
- **Concurrency.** Code written for one event loop may assume nothing else runs between two lines.
- **Configuration.** How `""`, `"0"` and `"false"` are read.
