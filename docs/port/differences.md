# Deliberate differences: RantAI-Agents TypeScript and Rust

Everything the new implementation does differently on purpose. If a behaviour differs and is not
here, it is a bug. The owner delegated these decisions (2026-11-14); each row names who made it.

| # | Where | Old behaviour | New behaviour | Why | Agreed by, date |
|---|---|---|---|---|---|
| 1 | Memory profile writes | In-process per-user promise lock (`lib/memory/profile-lock.ts`) plus compare-and-swap on `updatedAt` | Compare-and-swap (or `SELECT … FOR UPDATE`) only | The in-process lock does not hold across more than one instance | port lead, 2026-11-14 |
| 2 | Tool approval | Pending decisions in an in-process `Map`, 90 s timeout (`lib/tools/approval.ts:71-120`) | Pending decisions in Postgres or Redis | The stream and the approval POST may reach different instances | port lead, 2026-11-14 |
| 3 | Long-term memory, scope | `lib/memory/` holds the regex extractors (`extractEntities`, `extractFacts`, `detectContext`, `extractPermanentFacts`, `extractPreferences`), working memory, semantic recall and the long-term profile; the post-stream drain extracts facts out of every message, and the summary is generated by an LLM call inside the module | Only the long-term profile is ported (`agents-core/src/memory/`): the merge, collapse, apply and forget rules, the fingerprint, `summaryNeedsRefresh`, the prompt formatter and the memory tools. The extractors, working memory and semantic recall are not ported; the profile changes only through the `saveMemory`/`forgetMemory` tools and the summary. `MemoryConfig.working_memory` and `semantic_recall` are accepted and ignored, the tool result reports those slots as `not_enabled` and `skipped`, and the summary refresh (an LLM call) belongs to the store and LLM layers, not to the pure core | The port is meant to be lightweight, and a profile that fills itself from regex heuristics is what made the memory tools fire uninvited (TC-1548) | port lead, 2026-11-14 |
| 4 | Memory tool descriptions and the memory instruction | `saveMemory`: "Save durable personal facts, preferences, and entities the user has shared about themselves … DO NOT call this for search queries, conversation content, code, task instructions, or anything that is not a personal fact about the user." `forgetMemory`: "Delete stored personal memory about the user … Call it ONLY when the user explicitly refers to their own saved memory/profile facts. Examples: 'forget my location', 'hapus/lupakan data saya'. Returns exactly what was removed. DO NOT call this for generic commands (e.g. 'Tes hapus C'), for deleting chat messages, artifacts, code or files, for search/web requests, or when in doubt — ask the user instead of calling." The system prompt instruction (`lib/prompts/instructions.ts`, `CORRECTION_INSTRUCTION_WITH_TOOL`) says "When the user corrects or updates previously shared information … you MUST call saveMemory" and "you MUST call forgetMemory" | `saveMemory`: "Save a durable personal fact or preference that the user explicitly asks you to remember about themselves (for example 'remember that I live in Depok' or 'save that I prefer email'). A value for an existing label REPLACES the old value … Call it ONLY when the user asked you to remember something, or when they state a lasting personal fact or preference about themselves. DO NOT call it for search queries, conversation content, code, task instructions, or anything that is not a personal fact about the user." `forgetMemory`: "Delete personal memory you stored about the user before … Call it ONLY when the user explicitly asks you to forget or delete what is stored about them … DO NOT call it for generic delete commands (e.g. 'Tes hapus C'), for deleting chat messages, artifacts, code or files, for search or web requests, or for test phrases; when in doubt, ask the user instead of calling." The instruction says to save "ONLY when the user explicitly asks you to remember it … or when they state a lasting personal fact or preference about themselves that they want kept", and to forget "ONLY when the user explicitly asks you to forget or delete what is stored about them" | TC-1548: the tools fired without being asked. The old descriptions told the model to call the tool on every correction | port lead, 2026-11-14 |
| 5 | The interaction date in the prompt | `formatUserProfileForPrompt` printed `Interaction history: N conversations, last: <toLocaleDateString()>`, so the date depended on the locale and the time zone of the server | The same line with an ISO `YYYY-MM-DD` (UTC) | A prompt must not depend on the server's locale | port lead, 2026-11-14 |
| 6 | Reading a timestamp | `new Date(text)` reads ISO-8601 and loose formats ("2026", "2026-1-1", "Jan 1 2026"); a date-time without a zone is local time | Only ISO-8601 is read; a date-time without a zone is UTC; any other text counts as "no timestamp", which is what the old code did with a value `Date` could not read | The rows are written by the app with `toISOString()`, and the port must not depend on the server's time zone | port lead, 2026-11-14 |
| 7 | The stored row | A confidence of `1` is stored as `1`; `hydrateProfile` coerced the profile (an empty fact list, an empty summary, a zero count) but left a fact of the wrong type alone | A confidence of `1` is stored as `1.0` (`serde_json` keeps the difference between an integer and a float); a field of the wrong type is coerced the way `hydrateProfile` coerced it, and a fact list that is not an array becomes an empty list | The parity test compares the numbers by value; a row that is slightly off must not fail a chat request | port lead, 2026-11-14 |
| 8 | The ids of a stored fact or preference | `fact_<nanoid(10)>` / `pref_<nanoid(10)>`, generated inside the tool | The caller passes the id in | `agents-core` is pure: no randomness, no clock | port lead, 2026-11-14 |
| 9 | Memory routes, errors | `{"error": "<text>"}`; an unknown `?type=` reached Prisma and returned 500; the bulk DELETE ignored the parse result | The standard error body; unknown `type` and a bad body are 400 `invalid_request` | Best practice; QA backlog | port lead, 2026-11-14 |
| 10 | `DELETE /api/dashboard/memory/{id}` for another user's row | 403 `Forbidden` | 404 `not_found` | A 403 confirms the id exists | port lead, 2026-11-14 |
| 11 | Every authenticated Rust route | A suspended user's existing session or 30-day mobile token kept working (only login was blocked) | `suspendedAt` is checked on every request; suspended = 401 | QA TC-1269 | port lead, 2026-11-14 |
| 12 | LLM failures | The upstream error text was matched with a regex (`/401\|403\|unauthor\|api[_ ]?key/`) to pick what the user sees | The HTTP status picks it: 401/403 → the key message, 429 → the rate-limit message, everything else → the generic message | A regex over upstream wording misses the errors whose wording changes | port lead, 2026-11-14 |
| 13 | Token usage | Only OpenRouter sent `stream_options.include_usage`; house models (MiniMax) reported zero tokens | Every provider is asked for usage, so the cloud edition charges the real tokens | Usage the old code never received was a billing hole | port lead, 2026-11-14 |
| 14 | `<think>` extraction | The characters held back for a split tag are counted in UTF-16 code units (`src/lib/llm/strip-think.ts`) | They are counted in Unicode characters | The two differ only when the tail of a delta holds an astral character | port lead, 2026-11-14 |
| 15 | Tool approval in the loop | The tool's promise waited in memory for the approval POST, then the turn carried on | The executor answers "needs approval"; the loop stops and the caller decides what happens next | The approval store moves out of the process (difference 2), so the loop cannot wait | port lead, 2026-11-14 |
| 16 | Model routing | A model claimed by an admin-managed `LlmProvider` was served from that provider's endpoint and key, and `AI_PROVIDER_MODE=minimax` pinned every model to one MiniMax model outside production (`src/lib/llm/provider-registry.ts`, `src/lib/llm/provider.ts`) | `provider::route` knows the house models and OpenRouter; the managed registry and the dev override are the caller's job | Both need the database and the environment, and this crate does neither | port lead, 2026-11-14 |
| 17 | Dashboard sessions and messages, errors | `{"error": "<text>"}`; a body that was not JSON threw inside the route and became a 500; a wrong field was reported one at a time; an empty list of messages threw inside the Prisma transaction | The standard error body; a body that is not JSON, a missing field, a wrong type, an unknown field or a value that is too long is a 400 `invalid_request` with every bad field listed; an empty list of messages writes nothing and answers 200 | Best practice; the UI branches on `code` | port lead, 2026-11-14 |
| 18 | Another user's session, message or assistant | The session and the message answers were already 404; an assistant of another organisation was a 403 "You don't have access to this assistant"; an invitation that was never accepted counted as a membership | 404 `not_found` for all of them, and only an accepted membership opens an organisation's assistant | A 403 confirms that the id exists | port lead, 2026-11-14 |
| 19 | The edit history of a message | `sanitizeEditHistory` dropped a malformed entry silently and wrote an empty `editedAt`; the versions were lost after a refresh, and an older version showed the new user text next to the old answer | A malformed entry is a 400 naming the field that is wrong; every version keeps its user text and its assistant reply, and the history comes back in a fixed field order | The history is the user's data and must not be silently dropped (QA TC-944) | port lead, 2026-11-14 |
| 20 | A message id that already lives in another session | The repository threw and the route answered 500 | 409 `conflict` | The request conflicts with the state of the data; it is not a broken request | port lead, 2026-11-14 |
| 21 | `PATCH /api/dashboard/chat/sessions/{id}/messages` | It read the NextAuth session only, so a mobile token was refused | It takes the session cookie or the mobile Bearer token, like every other route of the group | The other routes of the group already took both | port lead, 2026-11-14 |
| 22 | Deleting a session | The route deleted the artifact rows, the S3 object of every archived version and the RAG chunks | The route deletes the artifact rows and the session (the messages go with the foreign key); the S3 objects and the RAG chunks stay | No S3 client and no vector store are ported yet | port lead, 2026-11-14 |
| 23 | The session list body | A bare array | The same bare array | The UI reads the array today; the conventions want `{ "data": [...], "nextCursor": ... }`, and the frontend moves in the slice that cuts the route group over | port lead, 2026-11-14 |
| 24 | The preview of the last message | `content.slice(0, 100)` counts UTF-16 code units, so a message of 100 emoji was cut in the middle of a code point | The first 100 characters (code points) | A Rust string cannot hold half a code point, and the preview is a preview | port lead, 2026-11-14 |
| 25 | Built-in assistants | Any logged-in user could edit a built-in assistant (`assistants/core/service.ts:203-233`) and write its bindings (`bindings/service.ts:33-44`: built-in = ok, no org or role check) | A built-in assistant is read-only for everyone except a platform admin: `Edit` and `EditBindings` need `actor.is_platform_admin`; `View` stays open to everyone and `Delete` stays closed to everyone (the old 403) | Plan §6: "any logged-in user can edit built-in assistants and their bindings" | port lead, 2026-11-14 |
| 26 | Assistant binding writes | `requireAssistantAccess` checked only that the caller's org matched (`bindings/service.ts:33-44`), so a viewer of the org could replace an assistant's tools, skills, MCP servers and workflows | Editing bindings requires the same as editing the assistant: same org plus a role that `can_edit` (`access::can` with `EditBindings`) | Plan §6: "Binding PUTs check the org but not the role" | port lead, 2026-11-14 |
| 27 | The system default assistant | One global `isSystemDefault` flag: setting a default cleared it for every organisation (`default/repository.ts:14-19`), and the permission lived only in the route guard (`app/api/assistants/[id]/default/route.ts`), not in the service or store | The default is per organisation (the store already scopes it), and the policy (`access::can` with `SetDefault`) requires `canManage` in the target's own organisation. A built-in or org-less assistant cannot be an organisation's default (the flag lives on the assistant row); an organisation with no default falls back to the built-in default, and choosing the built-in global default is a platform-admin task not ported yet | Plan §6: "Setting a system default clears it for every org" | port lead, 2026-11-14 |
| 28 | The JSON config columns | `memoryConfig`, `modelConfig`, `chatConfig` and `guardRails` were `z.unknown()`: any shape was stored, and a typo (e.g. `temperature: "hot"`, `toolApproval: "sometimes"`) lived in the column until chat read it | On create and update the four columns are validated against the typed configs in `assistant/config.rs`: field types, enum names and the numeric ranges (temperature 0–2, topP 0–1, penalties −2–2, `maxTokens` ≥ 1, non-negative whole counters); unknown keys inside a config are ignored, absent and `null` mean unset. Rows stored before this check are read through the same types when the prompt is built, so a value of the wrong type is left out: `requireCitations: 1` and `maxResponseLength: "500"` no longer add their rule, and a `blockedTopics` entry that is not a string is dropped | Plan §4: "`undefined`, `null` and absent keys in memoryConfig, modelConfig and guardRails (`z.unknown()` today, so anything goes)" | port lead, 2026-11-14 |
| 29 | The wizard's model and plan logic | `wizard/service.ts` queried the org plan, filtered the model catalog (`isFreePlan`, house models, `WIZARD_MODEL_ID`) and streamed | Not ported: model choice and plan checks belong to the caller (cloud), per plan §0 decision 2. `agents-core` keeps `buildWizardSystemPrompt` (with `is_free_plan` as its parameter, the model-rule text verbatim), `filterKnownIds` and `sanitizeProposal` | The port is meant to be lightweight and cloud-only behaviour is injected through callers | port lead, 2026-11-14 |
| 30 | The artifact prompt tables | `buildToolInstruction` embedded `CANVAS_TYPE_LABELS` and `assembleArtifactContext` from `lib/prompts/artifacts/**` (about 3,700 lines of per-type rules, examples and design tokens) | `agents-core/src/prompt/instructions.rs` ports the instruction's logic only: the artifact catalog (`labels`, `summary`, `full`) is passed in by the caller as an `ArtifactContext`; the tables stay in TypeScript until the chat slice ports them (`buildPlatformContextInstruction` and `LANGUAGE_INSTRUCTION` are chat-slice too) | A file-size-fitting slice; the branching logic, not static prompt text, is what needs parity | port lead, 2026-11-14 |
| 31 | The `{{date}}`/`{{time}}`/`{{datetime}}` variables | Resolved from `new Date().toLocale{Date,Time,}String()` — the value depended on the server's locale and time zone | Resolved from an ISO instant the caller passes; printed as `YYYY-MM-DD`, `HH:MM:SS` and `YYYY-MM-DD HH:MM:SS` | A prompt must not depend on the server's locale (same reason as row 5); `agents-core` has no clock | port lead, 2026-11-14 |
| 32 | Chat streaming, RAG sources | A non-standard `sources` frame appended **after** the `[DONE]` terminator (`chat-public/service.ts`, `appendSourcesEventToUiStreamResponse`: `data: {"type":"sources","sources":[…]}\n\n`); `X-RAG-Trace` is set alongside it. The dashboard does not use the SDK reader for it: it parses the stream itself (`transports/sse.ts` `consumeSseChunk`, the `"sources"` case in `chat-workspace.tsx`) | The sources go out as standard `source-document` chunks **before** `finish`, one per source: `sourceId` = the figure's asset key, else `<documentId>#<chunkIndex>`, else the document id, else the title; `mediaType` from the asset key's extension, `text/plain` without one; `title` = the document title; `filename` = the section; `providerMetadata.rantai` carries `page`, `assetKey`, `chunkType`, `chunkIndex`, `anchorChunkIndex` (nulls omitted). `X-RAG-Trace` is unchanged. `agents-contracts::ui_stream::legacy_sources_frame` still writes the old frame. **The dashboard has no `source-document` case today, so it shows no sources, pages or figure citations from the Rust stream until its reader changes: that UI change ships in the same slice as the RAG chat cutover (D4).** Numbers in every frame print as `JSON.stringify` prints them for integral floats and `-0`; a very small or very large float (`1e-7`, `1e21`) is written in Rust's notation, which parses to the same number | A frame after `[DONE]` is outside the protocol: the SDK's strict reader drops it and any other client has to special-case it; standard chunks are part of the `UIMessageChunk` union and survive SDK upgrades | port lead, 2026-11-14 |
